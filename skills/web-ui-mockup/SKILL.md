# Web UI Mockup

기존 웹 UI의 맥락을 보존하면서 사용자가 판단할 수 있는 목업을 만든다. 요청한 승인 경계에서 멈춘다.

## 산출물 선택

- **페이지 전체나 페이지 전환 목업:** 제작 전에 [전체 화면 목업 템플릿](references/full-page-preview.md)을 읽는다. 왼쪽 조작 패널과 오른쪽 전체 높이 미리보기를 갖춘 HTML을 만든다. 페이지 전환은 직접 실행하고 다시 재생할 수 있어야 한다.
- **부분 UI 목업:** 사이드바·메뉴·카드처럼 한 영역을 검토하면 기존 이미지 방식을 사용한다.
- 사용자가 산출물 형식을 별도로 지정하면 그 요청을 우선한다. 승인한 디자인의 제품 구현만 요청하면 이 스킬을 적용하지 않는다.

## 1. 요청과 현재 구조 확인

- 사용자의 목적, 수정 대상, 보존할 동작, 승인 시점을 짧게 정리한다. 이미 제공된 요구를 다시 질문하지 않는다.
- 첨부 스크린샷과 접근 가능한 프로젝트 지침, 관련 컴포넌트·스타일·실제 데이터를 읽는다. 표시값이 만들어지는 호출 흐름과 기존 아이콘·디자인 토큰을 확인한다.
- 코드 접근이 없으면 스크린샷을 근거로 작업하고 확인되지 않은 관계와 동작을 가정으로 표시한다.
- 이름만으로 항목의 역할을 추정하지 않는다. 분류·공용·참조·소유 관계가 있는 UI는 기존 데이터와 정책을 확인한다. 불확실한 관계는 보존하고 확인 필요로 남긴다.

## 2. 변경안을 시각적으로 구성

현재 디자인의 색상·글꼴·선택 표시를 기본값으로 삼는다. 사용자가 요청한 정보 밀도와 탐색 편의에 집중한다. 요청하지 않은 전체 리디자인을 추가하지 않는다.

| 대상 | 목업에 반영할 기준 |
| --- | --- |
| 정보 정리 | 반복된 설명을 줄이고 이름·주요 값의 시각적 우선순위를 높인다. 서로 다른 의미를 가진 정보는 중복으로 취급하지 않는다. |
| 아이콘 | 실제 역할에 맞는 일관된 계열·크기·선 굵기를 사용한다. 기존 라이브러리가 있으면 그 아이콘을 우선한다. 텍스트 이름도 함께 표시한다. |
| 계층 | 들여쓰기, 펼침 화살표, 그룹 구분을 유지한다. 소유 항목과 사용 참조를 섞지 않는다. |
| 상태 | 변경 판단에 필요한 기본·선택·펼침 상태를 보여준다. 폼이면 오류나 비활성 등 관련 상태를 선택한다. |
| 데이터 | 실제 이름과 대표 데이터를 사용한다. 긴 제목, 빈 상태, 작은 화면 등 관련 경계 사례를 확인한다. |

기본안 하나를 우선 제안한다. 부분 UI를 비교하면 같은 UI의 접힘·펼침 또는 변경 전·후를 나란히 놓는다. 전체 화면 후보는 왼쪽 패널에서 선택하고 오른쪽에 하나씩 크게 표시한다. 단순한 정리에 불필요한 디자인 후보를 만들지 않는다.

## 3. 독립 목업 제작

목업 파일은 임시 또는 지정된 시각화 출력 경로에 만들고 제품 소스와 분리한다. 전체 화면 목업은 위 템플릿을 적용한 HTML과 검수 캡처를 전달한다. 부분 UI 목업은 PNG처럼 대화에 표시할 수 있는 이미지를 전달한다. 텍스트 설명이나 ASCII 그림만으로 이미지 목업 요청을 완료하지 않는다.

- 정밀한 텍스트·목록·아이콘 UI는 기존 렌더러, HTML/CSS 또는 사용 가능한 이미지 그리기 도구로 만든다. 생성형 이미지가 필요한 그림·사진은 그에 맞는 이미지 도구를 사용한다.
- 로컬 렌더러는 설치된 도구와 글꼴부터 확인한다. 한국어 글꼴을 사용하고 특정 컴퓨터의 절대 글꼴 경로를 재사용 계약으로 삼지 않는다.
- 브라우저가 필요하면 연결된 브라우저의 정확한 작업 탭을 사용하고 프로젝트 브라우저 정책을 따른다.
- 이미지에는 실제로 들어갈 UI와 목업 설명을 구분한다. 범례나 설명을 실제 메뉴의 새 메타데이터처럼 끼워 넣지 않는다.
- 부분 UI 목업은 수정 영역과 판단에 필요한 주변 맥락을 충분한 크기로 보여준다. 전체 화면 목업은 오른쪽 미리보기 영역을 채우고 페이지 스크롤을 유지한다.

## 4. 렌더 결과 직접 검수

생성된 이미지 파일을 이미지 보기 도구로 열어 직접 확인한다. HTML을 사용했다면 해당 작업 탭을 캡처해 확인한다. 파일 생성 성공은 시각 검수를 대신하지 않는다.

확인할 항목:

- 마지막 행, 긴 이름, 하단 범례가 캔버스·패널 밖으로 잘리지 않는가?
- 한글이 정상 출력되고 실제 표시 크기에서 이름과 아이콘을 읽을 수 있는가?
- 아이콘·텍스트·화살표의 기준선과 들여쓰기가 일관적인가?
- 선택 상태와 계층이 명확하며 요청한 제거·추가 사항이 반영됐는가?
- 실제 등록 이름·개수·소유 관계와 맞는가? 예시 데이터는 예시라고 표시했는가?
- 전체 화면 목업이면 [템플릿 검수 항목](references/full-page-preview.md#검수)을 확인했는가?

문제가 있으면 수정하고 최종 파일을 다시 열어 확인한다. 정적 목업의 시각 검수와 제품의 동작·접근성 검증을 구분해 보고한다.

## 5. 전달과 승인 경계

최종 전달 전에 [wrapper-packages 등록 절차](references/wrapper-registration.md)를 읽고 적용한다. 검수한 후보를 `record`로 기록하고, 최종 응답에 각 후보의 실제 이미지·경로·URL을 넣는다. 후속 응답에서는 등록을 제안하고 사람의 승인을 기다린다. hook을 사용할 수 없으면 최종 전달에 등록 제안을 직접 넣는다.

최종 응답 순서:

1. 목업이 보여주는 상태를 한 문장으로 소개한다.
2. 이미지 자체를 표시한다. 전체 화면 목업이면 실행할 HTML 경로나 미리보기 URL도 넣는다. 로컬 파일과 이미지는 절대 경로를 사용한다.
3. 주요 변경점을 2~4개로 설명한다. 필요한 가정이나 제약도 짧게 밝힌다.
4. 사용자가 구현 전 승인을 요청했다면 “이 방향으로 적용할까요?”처럼 한 번 묻고 멈춘다. 제품 코드 수정 여부를 정확히 밝힌다.

예시 요청: “사이드 메뉴 항목 아래 반복 메타데이터를 없애고 아이콘을 붙이고 싶어. 목업부터 보여주고 승인받아줘.”

이에 대한 산출물은 실제 항목 이름을 사용한 기본 목록과 하위 항목 펼침 이미지, 제거한 정보·아이콘 기준 설명, 승인 질문이다. 그룹 제목·관계 정보와 각 행의 중복 메타데이터는 구분한다.

이미 특정 목업의 적용을 승인했다면 같은 승인을 반복 요청하지 않고 프로젝트의 구현 절차로 이어간다. 이 스킬 자체는 커밋·배포·외부 서비스 게시 권한을 추가하지 않는다.

제품 적용 승인과 `wrapper-packages` 등록 승인은 별개다. 등록을 승인받으면 위 절차에 따라 실제 소스와 기존 ID 계약을 확인한다. 등록 후에는 전체 `itemId`와 재사용 방법을 전달한다.
