# macOS Chrome 창 녹화

연결된 Chrome이 연속 영상 녹화를 지원하지 않고, 사용자가 현재 작업의 Chrome 창 녹화 방식을 허용했을 때 읽는다. 브라우저 조작은 계속 연결된 정확한 탭에서 수행한다.

## 사용 조건과 대상 확인

이 보조 도구는 AppKit·ScreenCaptureKit·AVFoundation과 `SCRecordingOutput`을 제공하는 macOS/Swift SDK를 사용한다. 현재 설치된 SDK로 컴파일해 지원 여부를 확인한다. 컴파일 실패를 전체 화면 캡처나 Playwright로 우회하지 않는다.

- 현재 승인된 대상과 방식, 실행 앱의 macOS 화면 기록 권한을 확인한다. OS 권한이 있다는 사실은 작업 승인을 대신하지 않는다. 과거 다른 프로젝트의 승인을 재사용하지 않는다.
- 권한 오류가 나면 아래 절차로 실행 제한과 OS 권한을 구분한다. helper는 권한 부여를 자동으로 요청하거나 설정을 바꾸지 않는다.
- 연결된 탭의 최신 ID·URL과 Chrome 창/profile을 대조한다. `list` 결과는 Chrome의 창 ID·프레임·제목이며, 제목만으로 탭의 URL 일치를 입증하지 못한다. 일치가 불명확하면 촬영을 시작하지 않는다.
- `desktopIndependentWindow` 필터는 지정한 Chrome 창만 녹화한다. 창 내부의 탭 전환도 녹화되므로 전용 창을 유지하고 다른 작업을 전환하지 않는다. 캡처는 한 번에 하나만 실행한다.

## 샌드박스 제한과 OS 권한 구분

`CGPreflightScreenCaptureAccess()`의 false나 helper의 `Existing macOS Screen Recording permission is required`는 **현재 실행 문맥에서 접근할 수 없다는 신호**다. 이 결과만으로 사용자가 OS 권한을 주지 않았다고 단정하지 않는다.

1. 현재 작업의 창 녹화 승인을 확인하고, 실패한 helper 경로·인자·오류와 샌드박스 실행 여부를 기록한다. 이미 받은 작업 승인은 다시 묻지 않는다. OS 권한과 도구의 실행 승인은 별개다.
2. 실행 환경의 승인 도구로 **동일 helper의 `list` 명령**을 샌드박스 밖에서 한 번 비교한다. Codex 셸에서는 `exec_command`의 `sandbox_permissions: "require_escalated"`와 대상·목적을 설명한 `justification`을 사용한다. 설정 변경이나 녹화로 진단하지 않는다. 다른 앱·도구로 제한을 우회하지 않는다.
3. 아래 결과에 따라 다음 행동을 정한다.

| 비교 결과 | 판단과 다음 행동 |
| --- | --- |
| 안에서는 실패, 승인된 밖에서는 `list` 성공 | 샌드박스 실행 제한을 원인으로 구분한다. OS 설정을 바꾸지 않고 필요한 창 녹화 명령만 승인된 실행 경로로 수행한다. |
| 승인된 밖에서도 같은 preflight/권한 오류 | 샌드박스만의 문제로 해결되지 않았다. 실제 실행 앱의 OS 화면 기록 권한과 앱 재시작 필요 여부를 확인하고, 권한이 없으면 사용자가 시스템 설정에서 허용하도록 안내한다. |
| 실행 승인이 거절되거나 밖에서 비교할 기능이 없음 | OS 권한 상태는 미확인으로 남긴다. 차단된 실행과 이유를 알리고 독립 작업을 계속한다. 자동 승인 검토가 거절했다면 그 사실·거절 이유·남은 작업을 설명하고 필요한 사용자 승인을 요청한다. |
| `list`는 성공하지만 대상 창이 없음 | OS 권한 오류로 되돌리지 않는다. 현재 탭/창과 프로필을 다시 찾아 연결한다. |

로컬 서버의 `listen EPERM` 같은 실행 제한도 별도로 기록한다. 이는 화면 기록 권한을 입증하거나 부정하는 근거가 아니다.

## 컴파일과 실행

아래 컴파일 명령은 이 스킬 디렉터리를 기준으로 한다. 프로젝트에 ignored 작업 경로가 있으면 원본과 바이너리는 그곳에 보존한다. 아래 `/tmp`는 임시 예시다.

```sh
capture_workdir=$(mktemp -d)
swiftc -parse-as-library \
  -module-cache-path "$capture_workdir/module-cache" \
  scripts/capture-window.swift \
  -o "$capture_workdir/capture-window"
"$capture_workdir/capture-window" --help
```

현재 창 녹화 승인을 확인한 뒤 창을 나열한다. 접근 오류는 위 진단 절차를 따른다.

```sh
"$capture_workdir/capture-window" list
```

record 형식은 다음과 같다. 인자는 모두 현재 작업에서 결정한 실제 값으로 바꾼다.

```text
capture-window record WINDOW_ID OUTPUT.mp4 SECONDS WIDTH_PX HEIGHT_PX FPS
```

`WIDTH_PX`·`HEIGHT_PX`는 최종 카드 크기가 아니라 raw 창 녹화의 출력 픽셀 크기다. 관찰한 창 크기와 배율로 결정하며, 이전 DPR을 적용하지 않는다. H.264 출력에 맞는 양의 짝수 크기를 사용한다. 새 `.mp4` 경로와 존재하는 부모 디렉터리를 지정한다. 도구는 기존 파일을 덮어쓰지 않으며 무음·커서 없음으로 기록한다. 소리나 커서 표시가 필수라면 이 helper의 제약을 밝히고 해당 기능을 지원하는 승인된 녹화 경로를 확인한다.

## 도구 포인터 표시 없이 촬영

`showsCursor=false`는 OS 커서를 숨긴다. Chrome 연결 도구가 페이지 안에 덧그리는 포인터 배지·클릭 하이라이트까지 없애는 옵션은 아니다. 샘플 영상의 실제 픽셀에서 따로 확인한다.

1. 녹화 전에 최신 화면에서 **크롭 밖의 비활성 영역**을 확인한다. 그곳으로 포인터를 옮길 수 있는 지원 입력을 사용하고 페이지 상태가 바뀌지 않았는지 확인한다. 좌표 클릭만 가능하면 링크·버튼·대화상자 backdrop이 아닌 안전한 지점을 고른다. 특정 좌표를 모든 페이지에 적용하지 않는다.
2. 해당 동작에 키보드 입력이 실제로 지원되면 현재 접근성 상태에서 대상을 찾아 포커스하고 조작한다. 링크/버튼 활성화에는 Return, 체크박스에는 Space, 지원되는 대화상자 취소에는 Escape를 사용할 수 있다. 매 입력 후 실제 값·열림 상태·포커스 복귀를 확인한다. 저장/닫기/취소의 의미가 다른 동작으로 바꾸지 않는다.
3. 열린 대화상자가 배지를 가릴 수 있으므로 **열기 전·스위치 변경 중·닫은 뒤**를 모두 샘플링한다. 배지가 남으면 오염된 촬영을 제외하고 재촬영한다. 필수 동작이나 UI를 잘라서 숨기지 않는다.
4. 사이트 자체 `:focus-visible` 테두리와 입력에 따른 내부 스크롤은 실제 UI다. 도구 표시와 구분해 보존한다. hover·drag처럼 포인터가 필수인 동작은 키보드로 대체해 같은 검증을 했다고 주장하지 않는다. 도구가 제공하는 표시 제어를 확인하고, 깨끗하게 촬영할 방법이 없으면 해당 샷의 제한으로 남긴다.

포커스 이동으로 내부 스크롤이 발생했다면 제목이 온전히 보이는 열림 초기 장면 등 의미 있는 시점에서 poster를 선택한다. 이 과정 때문에 원본 페이지의 CSS나 접근성을 변경하지 않는다.

## 촬영과 파일 마무리

1. 현재 웹 콘텐츠 경계와 raw 크기를 기록하고 짧은 샘플을 녹화한다. 창 프레임 좌표와 raw 영상 픽셀 좌표를 구분한다.
2. 실제 raw에서 콘텐츠 시작과 모든 경계를 확인한다. 브라우저 컨트롤과 안내 표시줄은 최종 크롭 바깥에 있어야 한다. 샘플 크롭으로 이를 검수한 뒤 본 촬영을 한다.
3. 실제 기록 시작 콜백을 확인한 `RECORDING` 출력 후 연결된 탭에서 예정된 입력을 수행한다. 화면 스트림 시작만으로 입력을 보내지 않는다. 재현 가능한 상태로 시작하고, 로딩·타이머가 필요한 샷은 녹화 시작과 상태 초기화의 순서를 맞춘다.
4. 프로세스가 정상 종료하고 `SAVED`가 나온 뒤 ffprobe로 출력 파일을 읽는다. 에러·종료 시간 초과·빈 파일은 성공으로 취급하지 않는다. helper는 같은 디렉터리의 고유한 임시 MP4에 기록하고 검증 후 요청 경로에 반영한다. 실패 시 보고된 임시 파일은 실패 원본으로 구분하고 최종 에셋에 사용하지 않는다.
5. 크롭과 최적화는 **web-video-optimize**에 맡긴다. 창/배율/viewport가 바뀌면 이전 측정을 폐기하고 새 샘플부터 확인한다.

도구는 `@MainActor`에서 `NSApplication.shared`를 초기화한다. 원래 사례의 CoreGraphics 초기화 문제를 피하기 위한 호출이므로 녹화 소스를 정리할 때 임의로 제거하지 않는다. 녹화 delegate의 오류와 정상 종료는 별도로 처리하며, 완료 콜백이 왔다는 사실만으로 성공을 판정하지 않는다.

## helper 검사

```sh
python3 scripts/test_capture.py
```

검사는 임시 경로에서 Swift를 컴파일하고 도움말·인자 검증·덮어쓰기 방지와 delegate의 시작/실패/완료 처리를 확인한다. 화면 조회나 녹화를 수행하지 않으므로 OS 권한·실제 창 선택·동작 품질까지 검증한 결과가 아니다. 실제 녹화 검증은 해당 작업의 승인 아래 샘플 촬영으로 수행한다.
