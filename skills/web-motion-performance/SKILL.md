# 웹 영상·애니메이션 성능 점검

기존 UI를 유지하면서 **같은 동작에서 반복되는 병목만** 측정하고 수정한다.
React, Vue, 일반 JavaScript에서 사용할 수 있다. 특정 프로젝트의 코드나 수치를 그대로 옮기지 않는다.

## 범위와 화면 고정

- 요청한 경로·동작·완료 조건을 짧게 정한다. 다른 작업자의 수정과 내 수정을 먼저 구분한다.
- 마지막으로 승인한 화면·영상·구현본의 위치와 상태를 기록한다. 기준이 없으면 현재 구현을 비교용으로 저장한다. 새 디자인을 확정하지 않는다.
- 구성·문구·배치·색상·영상 화질·효과·전환 시간·스크롤 곡선·반응형 동작을 유지한다. 보이는 영상의 동시 재생도 유지한다.
- 효과 삭제, 정지 이미지 대체, 해상도 저하로 수치를 높이지 않는다. UI 변경이 필요하면 이유와 영향을 제시하고 그 부분만 승인받는다.
- 기존 캐시·지연 로딩·중복 방지·자원 정리를 먼저 읽는다. 측정 도구와 수치는 임시 사본이나 별도 기록에 두고 제품 화면에 남기지 않는다.

## 수정 전 측정

1. 기존 성능 검사와 기준값을 확인한다. 경로, 빌드와 소스, 브라우저, 화면 크기와 DPR, 주사율, 영상 소스와 FPS를 기록한다.
2. 입력 순서·간격·시작 위치·측정 시간을 고정한다. 첫 진입, 재방문, 움직이는 상태, 쉬는 상태를 각각 비교한다.
3. 기존 표본 기준이 없으면 같은 조건으로 3회 측정해 시작한다. 독립 표본에서 같은 동작과 느린 작업이 다시 나타나는지 확인한다.
4. FPS와 프레임 간격의 p95·최대값·반복 지연 횟수를 함께 기록한다. 영상은 재생 프레임과 누락 프레임의 증가량도 확인한다.
5. 프로파일에서 반복 작업의 호출부와 시간을 찾는다. 공유 함수를 바꾸기 전에 모든 호출부와 생성·중지·재개·제거 흐름을 추적한다.

브라우저는 사용자가 허용한 연결 도구로 조작한다. 네이티브 창 제어 실패와 탭 연결 실패를 구분한다. 지원하는 탭에서 검사를 계속한다.

### 수치를 해석하는 기준

- `requestAnimationFrame` 호출률은 화면에 실제로 표시한 FPS와 다르다. 쉬는 화면의 낮은 호출률만으로 끊김을 판단하지 않는다.
- 수치를 올리려고 빈 애니메이션 루프를 추가하지 않는다. 움직인 상태와 쉰 상태의 결과를 섞지 않는다.
- 시스템 전체 GPU 사용률에는 다른 앱도 포함된다. 그 수치만으로 특정 페이지의 GPU 절감률을 주장하지 않는다.
- 긴 프레임 간격 전체가 한 함수의 실행 시간은 아니다. React로 표시된 작업도 실제 렌더링과 Effect 생성·정리 시간을 나눠 본다.
- 한 번 나온 최대 지연만으로 수정하지 않는다. 반복되지 않으면 관찰값으로 남긴다. 변동이 크면 원인과 표본 조건을 먼저 다시 확인한다.

## 확인한 원인에 맞춰 최소 수정

아래 방법을 일괄 적용하지 않는다. 반복 병목의 원인과 연결된 방법만 선택한다.

| 확인한 낭비 | 적용할 수정 | 유지할 동작 |
|---|---|---|
| 화면 밖 영상·텍스트 효과가 계속 실행됨 | 실제 가시성과 탭 상태에 따라 일시 중지 | 다시 보이면 기존 재생·타이머·타임라인을 재개 |
| 가려진 다음 영상이 먼저 재생됨 | 기존 마스크·겹침 상태로 실제 노출 구간 판단 | 보이는 두 영상과 승인한 전환 유지 |
| 멀리 있는 무거운 배경을 바로 준비함 | 보이기 전에 필요한 만큼 지연 준비 | 첫 노출 누락·깜빡임 방지, 취소한 준비 작업 정리 |
| 다시 스크롤할 때 같은 자원을 계속 생성함 | 이미 준비한 자원을 제한된 범위에서 재사용 | 화면 밖 계산 중지, 실제 제거 때 자원 해제 |
| 효과가 쉬거나 영상 프레임이 같아도 복사함 | 효과의 계산과 중복 업로드 중지 | 필요한 새 프레임·포인터 입력 때 갱신, 기본 영상 재생 유지 |
| 제거할 캔버스를 다시 할당한 뒤 버림 | 불필요한 할당을 생략하고 자원 해제 | 연결된 캔버스의 Effect 재설정과 실제 제거를 구분 |

동적 목록에서는 자원 수·메모리를 확인하고 보관 개수와 제거 조건을 정한다. 모든 영상과 GPU 문맥을 무제한 보관하지 않는다.
GPU 전송 API 교체는 브라우저·기기별 비교가 필요하다. 한 프로젝트에서 빠른 호출을 모든 프로젝트의 정답으로 만들지 않는다.

## 수정 후 판단

- 원인 하나씩 바꾼다. 수정 전과 같은 입력·환경·표본 기준으로 비교하고 원본 결과를 보관한다. 실패한 표본을 숨기지 않는다.
- 효과가 없거나 성능을 떨어뜨린 내 실험 변경은 제외한다. 다른 작업자의 변경은 되돌리지 않는다. 원인 없이 같은 실험을 반복하지 않는다.
- 같은 크기·상태에서 승인한 화면과 비교한다. 역방향 스크롤, 재진입, 탭 숨김, 모션 감소 설정과 자원 해제를 확인한다.
- 변경한 동작을 확인하는 작은 회귀 검사를 남기고 기존 검사도 실행한다. 빌드 통과를 UI 일치나 성능 유지의 근거로 쓰지 않는다.
- 반복 병목을 찾지 못했거나 측정 도구가 부족하면 그 한계를 보고한다. 검증한 성능 향상이 없으면 수정 없이 마쳐도 된다.

## 결과 설명

사용자에게 쉽게 설명한다. 무엇을 줄였는지, 같은 조건의 전후 수치, UI 유지 확인, 실행한 검사와 남은 한계를 적는다.
실제 표시 FPS를 측정하지 않았으면 rAF 호출률이라고 표시한다. 다른 프로젝트에서는 적용 조건과 확인 방법을 재사용한다.
